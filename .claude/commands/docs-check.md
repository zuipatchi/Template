# docs-check

ドキュメント全体を読み、**内部の品質**と**コードとの食い違い**の両方を検出して直す定期点検スキル。変更差分に関係するドキュメントだけを直すのは `/feature`・`/ship` の役割で、このスキルはドキュメント全体を横断的に見る。

**共通方針は [.claude/shared/check-policy.md](../shared/check-policy.md) に従う**（途中で確認を求めない・調査エージェントの使い方・直す／見送るの共通基準・修正時の注意・コミットと報告）。このファイルにはこのスキル固有の内容だけを書く。

**このスキルが書き換えるのはドキュメントだけ。** コード側の問題は直さず報告に回す（直すなら `/code-check` か `/feature`）。

## フロー

1. **調査** — 観点 A（内部品質）と観点 B（コードとの照合）を 2 エージェントで並列に調査する
2. **判断** — 指摘を統合し、直すか見送るかを決める
3. **修正** — 直すと決めた箇所を修正する
4. **コミット** — 1 コミットにまとめる
5. **報告** — 直したもの・見送ったもの（特にコード側の問題）を報告する

---

## Phase 1: 調査

対象は `docs/` 配下の全 .md・`CLAUDE.md`・`README.md`。共通方針「2. 調査エージェントの使い方」に従って、2 つの観点を並列に調査させる。

`CLAUDE.md`・`README.md`・`docs/` は役割が近く内容が重複・矛盾しやすいので、**3 者をまたいだ横断チェックを必ず行わせる**（例: 同じ説明が CLAUDE.md と docs/architecture.md の両方にある、README とドキュメントで手順が食い違う、CLAUDE.md の「主要ファイルの場所」と docs のリンク先がずれている）。

### 観点 A: 内部品質（コードの中身は読まない）

| カテゴリ | 検出内容 |
|---|---|
| 矛盾 | 同じ事項について別々のドキュメント（または同一ドキュメント内）で食い違う記述（数値・命名・手順・方針など） |
| 重複 | 同じ説明・表・コード例が複数箇所にある。一方に集約して他方からリンクすべき箇所 |
| リンク切れ | `[テキスト](パス)` のリンク先ファイル・`#見出し` アンカーが実在するか。**Glob でファイルの存在を、Grep で見出しの存在を必ず確かめる**（推測で「切れている」と書かない。`%20` などの URL エンコードにも注意） |
| 古い記述 | 「TODO」「未実装」「予定」など実態と合っていなさそうな記述、削除済み機能の残骸、日付・バージョン番号の古さ |
| 構成の崩れ | 見出し階層の飛び（h2 の次に h4 など）、目次と見出しのずれ、表のカラム不揃い |
| 誤字・表記ゆれ | 明らかな誤字、同一用語の表記ゆれ（例: Addressable / Addressables、LifetimeScope / LifeTimeScope）、コード例の規約違反・未定義変数 |

### 観点 B: コードとの照合

- CLAUDE.md の「主要ファイルの場所」など、ドキュメント内のすべてのファイルパスが実在するか（Glob で確認）
- ドキュメントが言及しているクラス・メソッド・プロパティ・定数・USS クラス・UXML 要素名が、シグネチャや引数まで含めて実際のコードに存在するか（該当コードを全文読んで確認）
- アーキテクチャ・DI 登録（LifetimeScope・Lifetime・登録方法）・シーン構成・遷移フローの説明がコードと一致しているか
- 数値（フェード時間・sortingOrder・音量・色など）が実装と一致しているか
- docs/product.md の機能一覧が実装と一致しているか
- docs のコード例・手順（patterns.md の追加手順など）が現在のコード構成で成り立つか
- CLAUDE.md のテスト構成・注意点がテストコードと一致しているか

食い違いは、**ドキュメントの該当行**と**実コードの実態（ファイルと行）**を両方報告させる。

## Phase 2: 判断

両エージェントの報告を統合する。**同じ箇所が両方の観点で指摘されたら 1 件にまとめる**（例: 削除済みファイルへのリンクは、内部品質のリンク切れでもありコードとの食い違いでもある）。

共通方針「3. 直す／見送るの共通基準」に加えて、次の基準を使う。

**観点 A（内部品質）**:
- 明確なもの（誤字・リンク切れ・表記ゆれ・単純な構成崩れ）はそのまま直す
- 矛盾のどちらを正とするかは、`git log -p` で新しく書かれた側・意図的に変えられた側を確認して決める（新しい記述のほうが正の可能性が高い）。実装が絡む矛盾は、必要な範囲だけコードを読んで実態に合わせる
- 重複は「どちらが主題のドキュメントか」で集約先を決める（例: アーキテクチャの詳細は docs/architecture.md、CLAUDE.md は要点とリンク）

**観点 B（コードとの照合）** は、食い違いを 3 種類に分ける:

| 種別 | 判断基準 | 対応 |
|---|---|---|
| ドキュメントが古い | コードが正しい実装で、ドキュメントが旧仕様を指している | ドキュメントを直す |
| コードが未実装・誤実装 | ドキュメントの記述があるべき姿で、コードが追いついていない | **コードは触らず**見送り、ファイルと行を添えて報告する |
| どちらが正か不明 | 決まらない | `git log -p` で新しい側を確認 → 実装と呼び出し元を読んで実際の挙動を確定 → 他ドキュメントの多数側・主題側に合わせる。それでも決まらなければ見送る |

---

## Phase 3: 修正

共通方針「4. 修正時の注意」に従う。加えて:

- **重複の集約**: 最も適切な 1 か所に内容を残し、他方は要約と該当箇所へのリンクに置き換える（情報を二重管理しない）
- **リンク切れ**: 正しいパス・アンカーに直す。リンク先が消えていれば記述ごと見直す
- **削除された API・定数・ファイル**: 記述ごと削除する
- **新しく追加された API**: 漏れなく追記する
- **誤字・表記ゆれ**: 既存ドキュメントで多数派の表記に合わせる
- 文体・スタイルは既存ドキュメントに合わせ、検出した問題以外の文言改善・リライトはしない

---

## Phase 4: コミット

```
docs: <変更の要点>
```

例: `docs: リンク切れと表記ゆれを修正し、ISceneReady の実装例をコードに合わせる`

---

## Phase 5: 報告

共通方針「5. コミットと報告」の形式で報告する。見送ったもののうち**コード側が未実装・誤実装**と判断したものは、ユーザーが対処できるようファイルと行を添えて別枠で挙げる。
