# sync-docs

ドキュメントとコードの乖離を検出・修正するスキル。

**このスキルは途中でユーザーに確認を求めず、修正とコミットまで自分で完結する。** 判断に迷う乖離は「聞く」のではなく、Phase 2 の基準で見送って最後に報告する。

## フロー

1. **調査** — Explore エージェントにドキュメントとコードを横断的に照合させる
2. **分類と判断** — 乖離を仕分けし、直すもの／見送るものを自分で決める
3. **修正** — 乖離箇所を Edit ツールで修正する
4. **コミット** — 変更をコミットする
5. **報告** — 直した内容と見送った内容をまとめて報告する

---

## Phase 1: 調査

Explore エージェントを spawn して以下を調査させる。エージェントへの指示：

- `docs/` 配下の全 .md ファイルを読む
- `CLAUDE.md` を読む
- CLAUDE.md の「主要ファイルの場所」テーブルに列挙されたパスが実際に存在するか確認する
- 各ドキュメントが言及しているクラス・メソッド・プロパティ・定数が実際のコードに存在するか確認する
- ゲームルールや計算式が記述されている場合、実装と一致しているか確認する
- アーキテクチャ・DI 登録・フロー説明がコードと一致しているか確認する

乖離の候補が見つかったら、**ドキュメントの該当行** と **実コードの実態** を両方報告させる。

---

## Phase 2: 乖離の分類と判断

エージェントの報告を受けて、乖離を以下の 3 種類に分類する：

| 種別 | 判断基準 | 対応 |
|---|---|---|
| ドキュメントが古い | コードが正しい実装で、ドキュメントが旧仕様を指している | ドキュメントを修正する |
| コードが未実装・誤実装 | ドキュメントの記述が正しく、コード側が追いついていない | **コードは触らず**見送り、最終報告に残す |
| どちらが正か不明 | ドキュメントとコードのどちらを直すべきか決まらない | 下記の裏取りを行い、決まらなければ見送る |

「どちらが正か不明」の裏取り手順（この順で確かめる）：

1. `git log -p -- <該当ファイル>` で、ドキュメントとコードのどちらが後から更新されたかを見る。新しい側が「正」の可能性が高い
2. 該当コードの実装と呼び出し元を読み、実際に動いている挙動を確定させる
3. 他のドキュメント（docs/product.md など）に同じ事項の記述があれば、多数側・主題側に合わせる

裏取りしても決まらない乖離は、**手を付けずに見送る**。特に以下は必ず見送る：

- 直すには仕様・プロダクト方針の決定が必要になるもの
- ドキュメントの記述が「あるべき仕様」で、コードがそれに追いついていないもの（**このスキルでコードを実装・修正しない**）
- ドキュメント全体の章構成を変える必要があるもの

修正時の注意：
- 削除した API・定数があれば記述ごと削除する（「削除済み」コメントを残さない）
- 新しく追加された API があれば漏れなく追記する
- 文体・スタイルは既存ドキュメントに合わせる

---

## Phase 3: コミット

修正が完了したらコミットする。複数ファイルを修正した場合も 1 コミットにまとめてよい。

コミットメッセージの形式：
```
ドキュメント修正（<変更の要点>）
```

例：
```
ドキュメント修正（DeckModel API・デッキ構築ルール・CPUデッキの乖離を解消）
```

乖離が 1 つも無かった場合はコミットせず、その旨を報告して終了する。

---

## Phase 4: 報告

最後にまとめて報告する（確認ではなく事後報告なので簡潔に）：

- 直した乖離（ファイル単位でまとめる）
- 見送った乖離とその理由。特に「コード側が未実装・誤実装」と判断したものは、ユーザーが対処できるようファイルと行を添えて挙げる
- コミットハッシュ

---

## 注意事項

- コードを読まずにドキュメントだけを書き換えない。必ず実装を確認してから修正する
- ファイルパスの確認は Glob ツールで行う（存在しないパスを「存在する」と書かない）
- メソッド・プロパティの確認は Grep ツールで行う
- 修正範囲は乖離箇所のみ。無関係なリファクタや文言改善は行わない
- **このスキルが書き換えるのはドキュメントだけ**。コード側の修正は行わず、報告に回す
