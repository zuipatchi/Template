# duplicate-check

コードの重複・冗長な実装を検出して整理するスキル。

**このスキルは途中でユーザーに確認を求めず、修正とコミットまで自分で完結する。** 判断に迷う重複は「聞く」のではなく、Phase 2 の基準で見送って最後に報告する。

## フロー

1. **調査** — Explore エージェントに重複を横断的に探させる
2. **判断** — 見つかった重複を仕分けし、直すもの／見送るものを自分で決める
3. **修正** — 直すと決めた箇所を Edit ツールで修正する
4. **コミット** — 変更をコミットする
5. **報告** — 直した内容と見送った内容をまとめて報告する

---

## Phase 1: 調査

Explore エージェントを spawn して以下を調査させる。エージェントへの指示：

- `Assets/Scripts/` 配下の全 `.cs` ファイルを対象とする
- 以下のカテゴリで重複・冗長箇所を探す：

  **ロジックの重複**
  - ほぼ同一の処理フローを持つメソッド（引数が少し違うだけ、など）
  - 同じ計算式・条件分岐が複数ファイルにコピーされている
  - エラーハンドリングパターン（`catch (OperationCanceledException) { }` の後に同じ処理）

  **定数・設定値の重複**
  - 同じ文字列リテラル（セッション名 `"QuickMatch"` など）が複数箇所に直書き
  - 同じ数値（タイムアウト秒数、プレイヤー人数など）が散在

  **UI クエリの重複**
  - `root.Q<T>("name")` で同じ要素を別々のメソッドで取得している

  **状態判定の重複**
  - 同じ `MatchingState` の組み合わせ判定が複数メソッドに存在する

- 各重複について以下を報告させる：
  - **ファイルパスと行番号**（両方の箇所）
  - **重複の種類**（ロジック／定数／UI クエリ／状態判定）
  - **重複度合い**（完全一致／ほぼ同じ／パターンが同じ）
  - **統合の難易度**（簡単／要検討）

---

## Phase 2: 判断

エージェントの報告を受けて、**各重複を直すかどうか自分で決める**。ユーザーには聞かない。

**直す**:
- 重複度が「完全一致」「ほぼ同じ」で、統合しても外部から見た振る舞いが変わらないもの
- 難易度「要検討」でも、影響範囲を Grep で全件洗い出せて、変更が既存クラス内（または同一アセンブリ内）に収まるもの

**見送る**（手を付けず、理由つきで最終報告に残す）:
- 重複度が「パターンが同じ」だけのもの。偶然似ているだけの箇所を無理に統合しない（過度な抽象化をしない）
- 統合すると振る舞いが変わる、または変わらないと確信できないもの
- `public` / `internal` の API シグネチャ変更や、新しい共通クラス・インターフェースの新設が必要になるもの（設計方針の決定にあたる）
- アセンブリ（asmdef）をまたぐ共通化が必要なもの
- 実装の差分が「意図的に分けてある」可能性が読み取れるもの（コメント・命名・呼び出し文脈から判断する）
- テストコードの重複（テストは意図的に明示的に書くためスコープ外）

判断材料が足りないときは、聞く前に自分で埋める：該当コードと呼び出し元を読む、`git log -p` で片方だけ後から変えられていないか確認する。それでも決められなければ見送る。

---

## Phase 3: 修正

直すと決めた箇所を修正する。

修正の優先順位：
1. **定数の重複** — `private const string` または `private static readonly string` に抽出
2. **UI クエリの重複** — すでに `Awake` で取得済みのフィールドを使い回す
3. **状態判定の重複** — `private bool IsXxx(MatchingState state)` などのヘルパーに抽出
4. **ロジックの重複** — `private async UniTask XxxAsync(...)` に抽出してそれぞれから呼ぶ

修正時の注意：
- コーディング規約（CLAUDE.md）を守る：`_camelCase`、`var` 不使用、アクセス修飾子必須
- 動作を変えない。リファクタのみ。振る舞いが変わる統合は Phase 2 の基準に従って見送る
- 抽出したメソッド・定数は既存コードのすぐ近くに置く（見通しを悪くしない）

修正後の自己検証（コンパイルできないので読みで確かめる）：
- 置き換え漏れがないか Grep で旧リテラル・旧コードパターンを全件確認する
- 抽出先のアクセス修飾子・`static` の有無が呼び出し元と噛み合っているか確認する
- `Assets/Tests/` 配下から参照されているメンバーを動かしていないか確認する

---

## Phase 4: コミット

修正が完了したらコミットする。

コミットメッセージの形式：
```
重複コードを整理（<変更の要点>）
```

例：
```
重複コードを整理（QuickMatch 定数化・エラーハンドリングを共通化）
```

直す対象が無かった場合はコミットせず、その旨を報告して終了する。

---

## Phase 5: 報告

最後にまとめて報告する（確認ではなく事後報告なので簡潔に）：

- 整理した重複（種類ごとに、どこをどこへ寄せたか）
- 見送った重複とその理由（ユーザーの判断が必要なものはここに集める）
- コミットハッシュ

---

## 注意事項

- 判断に迷ったら「ユーザーに聞く」のではなく「見送って報告する」。手を付けた箇所は必ず根拠を持って直しきる
- 重複度が低い（「パターンが似ているだけ」）場合は無理に統合しない。過度な抽象化はしない
- テストコードの重複はスコープ外（テストは意図的に明示的に書くため）
