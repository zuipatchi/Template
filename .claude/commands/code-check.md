# code-check

`Assets/Scripts/` 配下のコード全体を読み、問題を検出して直す定期点検スキル。変更差分だけを見るのは `/feature`・`/ship` の検証ループの役割で、このスキルは**既存コードも含めて横断的に**見る。

**共通方針は [.claude/shared/check-policy.md](../shared/check-policy.md) に従う**（途中で確認を求めない・調査エージェントの使い方・直す／見送るの共通基準・修正時の注意・コミットと報告）。このファイルにはこのスキル固有の内容だけを書く。

## フロー

1. **調査** — 観点 A〜F を 1 観点 1 エージェントで並列に調査する
2. **判断** — 指摘を統合し、直すか見送るかを決める
3. **修正** — 直すと決めた箇所を修正する
4. **コミット** — 1 コミットにまとめる
5. **報告** — 直したもの・見送ったものを報告する

---

## Phase 1: 調査

調査範囲は `Assets/Scripts/` 配下全体（関連する UXML / USS / asmdef / LifetimeScope / シーンの設定も裏付けのために読む）。ユーザーが特定のファイル・ディレクトリを指定した場合のみそこに絞る。テストコード（`Assets/Tests/`）は調査対象外。

観点 A〜F を、共通方針「2. 調査エージェントの使い方」に従って並列に調査させる。各エージェントには CLAUDE.md の規約も伝える。

### 観点 A: バグ・不具合

- **null 参照の可能性**: `[Inject]` 漏れ・`Q<T>` の取得失敗（要素名タイポ。UXML と照合する）・null チェックなしの参照
- **非同期の例外握りつぶし**: `async void`、await し忘れ（fire-and-forget）、`catch { }` で例外を黙殺、`OperationCanceledException` の扱い漏れ
- **R3 の購読リーク**: `Subscribe` の戻り値を `AddTo` / `Dispose` していない、`ReactiveProperty` の破棄漏れ
- **CancellationToken の伝播漏れ**: トークンを受け取れるのに渡していない、画面破棄後に走り続ける処理
- **競合・順序依存**: 初期化前アクセス、`await` を跨いだ状態の前提崩れ、二重実行ガードの欠如
- **境界・分岐の取りこぼし**: 空コレクション・最大値などのエッジケース、switch の default 漏れ

### 観点 B: 規約違反（CLAUDE.md）

命名・`var`・`new()`・readonly・波括弧・using の順序と位置は `dotnet format` で検出できる（Phase 3 の自己検証で拾える）。エージェントには、それ以外の規約（DI 禁止事項・アセット読み込み・UI・USS）を中心に探させる。

- **命名**: フィールドが `_camelCase` でない、型・メソッド・プロパティ・定数が `PascalCase` でない
- **`var` の使用**、型が明らかな生成で `new()` を使っていない
- **アクセス修飾子の欠如**、readonly にできるフィールドが readonly でない
- **波括弧の省略**（単一行の `if (...) return;` を含む）
- **DI 禁止事項**: `GameObject.Find` / `FindObjectOfType` / static 経由の依存取得
- **アセット読み込み**: `Resources.Load` の使用（Addressables を使うべき）
- **UI**: uGUI の使用、UXML の `style` 属性や C# の `element.style.*` による見た目の定義（表示/非表示・アニメーション中の値は除く）
- **USS 非サポートプロパティ**: `gap` / `row-gap` / `column-gap`、`-unity-background-scale-mode: scale-to-fill`

### 観点 C: 設計・アーキテクチャの逸脱

docs/architecture.md・docs/patterns.md に意図が書かれている設計は逸脱扱いしない。

- **単方向フロー違反**: Presenter が Model を経由せず直接状態を書き換える、View が Model を直接参照する
- **責務の混在**: Model に UI 処理、Presenter にビジネスロジックの塊
- **DI の誤用**: LifetimeScope への登録漏れ／二重登録、スコープ違い、`[Inject]` されるのに登録されていない型
- **ReactiveProperty の使いどころ**: 状態なのに普通のフィールド、逆に状態でないものを ReactiveProperty に
- **シーン構成**: Common 常駐前提の崩れ、アディティブロードの想定外

### 観点 D: パフォーマンス

指摘する前に、その処理の呼び出し頻度（毎フレームか、画面遷移時に 1 回か）を呼び出し元から確認させる。

- **毎フレーム処理**（`Update`、UniTask の Yield ループ、DOTween の setter 等）内の重い処理（LINQ アロケーション、`Q<T>` 呼び出し、文字列生成、`new` の連発）
- **キャッシュすべき参照の都度取得**: `root.Q<T>("name")` を毎回呼ぶ
- **不要なアロケーション**: ループ内のラムダキャプチャ、`ToList()` / `ToArray()` の乱用
- **Addressables / 音声ロードの非効率**: 同じアセットの多重ロード、解放漏れ
- **DOTween の Kill 漏れ**（オブジェクト破棄後も動き続ける）

### 観点 E: 重複・冗長

重複と判断する前に、候補同士のコードを並べて読み、本当に同じ処理か（引数・前提条件・副作用の違いがないか）を確認させる。

- **ロジックの重複**: ほぼ同一の処理フローを持つメソッド、同じ計算式・条件分岐のコピー、同じエラーハンドリングパターン
- **定数の重複**: 同じ文字列リテラル（PlayerPrefs のキー、UXML の要素名など）や数値（フェード時間、点滅間隔、音量の初期値など）の直書き
- **UI クエリの重複**: `root.Q<T>("name")` で同じ要素を別々のメソッドで取得している
- **状態判定の重複**: 同じ列挙型（`Scenes` など）の組み合わせ判定が複数メソッドにある

追加で報告させる項目: **重複度合い**（完全一致／ほぼ同じ／パターンが同じ）、**統合先**（同一クラス内で済むか、アセンブリをまたぐか、新クラスや public API の変更が要るか）、差分が意図的に見えるか。

### 観点 F: ファイル分割

全ファイルの行数一覧も報告させる。

- **行数**: 200 行を超えるファイル
- **責務の混在**: 1 つのクラスが複数の責務を持っている（観点 C と重なる場合は、ファイルを分けて解決するものをこちらで扱う）
- **public メソッドが多い**: インターフェース分割の余地
- **依存の膨張**: `[Inject]`（コンストラクタ・メソッド注入とも）で受け取る依存が 4 つ以上
- **1 ファイルに複数の公開型が同居**して見つけにくい

追加で報告させる項目: **分割案**（どのクラス・ファイルに切り出すか）、**影響**（シーン・Prefab のコンポーネント付け替え、UXML/USS/Addressables の変更、asmdef の移動、LifetimeScope の登録変更が要るか）。

## Phase 2: 判断

各エージェントの報告を統合する。**複数の観点で同じ箇所が指摘されたら 1 件にまとめて 1 回だけ判断する**（例: 依存の膨張（F）と効果音の重複（E）が同じ解決策を指す場合）。

共通方針「3. 直す／見送るの共通基準」に加えて、観点ごとに次の基準を使う。

| 観点 | 直す | 見送る |
|---|---|---|
| A バグ | `AddTo` 漏れ、`CancellationToken` の受け渡し漏れ、`catch { }` へのログ追加など、正しい挙動が一意に決まるもの | `async void` → `async UniTaskVoid` のうち、Unity のイベントや `IAsyncStartable` など呼び出し側がシグネチャを要求しているもの。エラー時の復帰方法など仕様判断を含むもの |
| B 規約 | 機械的に直るもの | UXML / USS の変更が必要で、どちらを直すべきか決まらないもの |
| C 設計 | 局所的に直るもの | クラスの分割・DI の再設計・責務の移動といった大きなリファクタ |
| D パフォーマンス | キャッシュ化など、挙動が変わらない明確な改善 | 計測なしに効果を判断できないもの |
| E 重複 | 「完全一致」「ほぼ同じ」で、同一クラス内または同一アセンブリ内の private / internal / protected なヘルパーに寄せられるもの | 「パターンが同じ」だけのもの（無理に抽象化しない）。アセンブリをまたぐもの。新しい公開クラスが必要なもの。差分が意図的に見えるもの |
| F 分割 | 影響範囲を Grep で確定でき、DI 登録の変更が LifetimeScope 内で完結するもの | MonoBehaviour の分割でシーン・Prefab の付け替えが必要なもの。asmdef をまたぐ移動。行数は多いが責務が 1 つで、切ると読みにくくなるもの |

## Phase 3: 修正

共通方針「4. 修正時の注意」に従う。観点 E・F は次の点にも気をつける。

- **重複の統合**の優先順位: 定数の抽出 → 取得済みフィールドの使い回し → 状態判定のヘルパー化 → ロジックのヘルパー化。抽出したメソッド・定数は既存コードのすぐ近くに置く
- **ファイル分割**: 既存の名前空間・ディレクトリ構成を維持する。新しい `.cs` を作ったら `.meta`（`fileFormatVersion: 2` と新しい `guid`）も作る。docs や CLAUDE.md が旧ファイルの場所を参照していればリンクも直す

---

## Phase 4: コミット

観点をまたいでいても 1 コミットにまとめる。

```
コードの問題を修正（<変更の要点>）
```

例: `コードの問題を修正（購読リーク・var 違反を解消、音量キーを定数化、Scenes enum を分割）`

---

## Phase 5: 報告

共通方針「5. コミットと報告」の形式で報告する。指摘には `[観点/深刻度]` を付ける（例: `[バグ/高] SceneTransitioner.cs:61`）。
