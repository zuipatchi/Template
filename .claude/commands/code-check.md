# code-check

`Assets/Scripts/` 配下のコードを読み、おかしなところを検出して直すスキル。

**このスキルは途中でユーザーに確認を求めず、修正とコミットまで自分で完結する。** 判断に迷う指摘は「聞く」のではなく、Phase 2 の基準で見送って最後に報告する。

重複検出は duplicate-check、ファイル分割は split-check の担当。このスキルはそれらと被らない「バグ・規約違反・設計逸脱・パフォーマンス」を対象とする。

## フロー

1. **調査** — Explore エージェントを観点別に並列で spawn して問題を洗い出す
2. **判断** — 各指摘を直すか見送るか自分で決める
3. **修正** — 直すと決めた箇所を Edit ツールで修正する
4. **コミット** — 変更をコミットする
5. **報告** — 直した内容と見送った内容をまとめて報告する

---

## Phase 1: 調査

**調査範囲は `Assets/Scripts/` 配下全体**（変更差分だけでなく既存コードも含めて横断的に見る）。ユーザーが特定ファイル・ディレクトリを指定した場合のみそこに絞る。

Explore エージェントを**観点別に並列で** spawn する（1観点1エージェント）。各エージェントには `Assets/Scripts/` 配下全体を対象とすること、CLAUDE.md の規約を伝え、以下を調べさせる。

### 観点A: バグ・不具合

- **null 参照の可能性**: `[Inject]` 漏れ・`Q<T>` の取得失敗（要素名タイポ）・null チェックなしの参照
- **非同期の例外握りつぶし**: `async void`、await し忘れ（fire-and-forget）、`catch { }` で例外を黙殺、`OperationCanceledException` の扱い漏れ
- **R3 の購読リーク**: `Subscribe` の戻り値を `AddTo` / `Dispose` していない、`ReactiveProperty` の破棄漏れ
- **CancellationToken の伝播漏れ**: トークンを受け取れるのに渡していない、画面破棄後に走り続ける処理
- **競合・順序依存**: 初期化前アクセス、`await` を跨いだ状態の前提崩れ、二重実行ガードの欠如
- **境界・分岐の取りこぼし**: 空コレクション・最大値などのエッジケース、switch の default 漏れ

### 観点B: 規約違反（CLAUDE.md）

- **命名**: フィールドが `_camelCase` でない、型・メソッド・プロパティ・定数が `PascalCase` でない
- **`var` の使用**（このプロジェクトは明示的な型のみ）
- **アクセス修飾子の欠如**
- **波括弧の省略**、開き波括弧が同一行
- **DI 禁止事項**: `GameObject.Find` / `FindObjectOfType` / static 経由の依存取得
- **アセット読み込み**: `Resources.Load` の使用（Addressables を使うべき）
- **UI**: uGUI の使用（UI Toolkit を使うべき）、スタイルのインライン指定（USS に置くべき）
- **USS 非サポートプロパティ**: `gap` / `row-gap` / `column-gap`、`-unity-background-scale-mode: scale-to-fill`
- **using 位置**: 名前空間の内側に書かれた using

### 観点C: 設計・アーキテクチャの逸脱

- **単方向フロー違反**: Presenter が Model を経由せず直接状態を書き換える、View が Model を直接参照する
- **責務の混在**: Model にUI処理、Presenter にビジネスロジックの塊、Service が通信・変換・状態を全部持つ
- **DI の誤用**: LifetimeScope への登録漏れ／二重登録、スコープ違い（Common に置くべきものを各シーンに、など）
- **ReactiveProperty の使いどころ**: 状態なのに普通のフィールド、逆に状態でないものを ReactiveProperty に
- **シーン構成**: Common 常駐前提の崩れ、アディティブロードの想定外

### 観点D: パフォーマンス

- **`Update` / 毎フレーム処理**内の重い処理（LINQ アロケーション、`Q<T>` 呼び出し、文字列生成、`new` の連発）
- **キャッシュすべき参照の都度取得**: `root.Q<T>("name")` を毎回呼ぶ（Awake でキャッシュすべき）
- **不要なアロケーション**: ループ内のラムダキャプチャ、`ToList()` / `ToArray()` の乱用
- **Addressables / 音声ロードの非効率**: 同じアセットの多重ロード、解放漏れ

### 各エージェントへの報告指示

各問題について以下を報告させる：

- **ファイルパスと行番号**
- **観点**（バグ／規約／設計／パフォーマンス）
- **深刻度**（高＝動作不良やクラッシュ・クラッシュ寸前 ／ 中＝潜在バグや明確な規約違反 ／ 低＝改善提案）
- **何が問題か**（1〜2文）
- **確信度**（確実／要確認）— 文脈次第で問題でない可能性があるものは「要確認」にする
- **修正案**（どう直すか。1〜2文）

## Phase 2: 判断

各エージェントの報告を統合し、**指摘ごとに直すか見送るか自分で決める**。ユーザーには聞かない。

**直す**:
- 確信度「確実」で、修正が局所的（そのファイル・そのメソッド内で完結する）なもの
- 規約違反（`var` → 明示型、命名、アクセス修飾子、波括弧など機械的に直るもの）
- 明確なバグ修正で、正しい挙動が一意に決まるもの（`AddTo` 漏れ、`CancellationToken` の受け渡し漏れ、`catch { }` へのログ追加、default 漏れなど）
- キャッシュ化などの明確なパフォーマンス改善で、挙動が変わらないもの
- 確信度「要確認」でも、**該当コードと呼び出し元を自分で読んで確実だと確定できたもの**（憶測のまま直さない）

**見送る**（手を付けず、理由つきで最終報告に残す）:
- コードを読んでも「問題かどうか」が確定しないもの（意図的な実装の可能性が残るもの）
- 修正が**振る舞いの変更**になるもの、または正しい挙動が一意に決まらないもの（エラー時にどう復帰させるか等の仕様判断を含む）
- `async void` → `async UniTaskVoid` などシグネチャ変更を伴うもののうち、Unity のイベントハンドラや `IAsyncStartable` など**呼び出し側がシグネチャを要求している**可能性があるもの
- シーン（`.unity`）・Prefab・UXML・USS・Addressables 側の変更が必要なもの（例: `Q<T>` の要素名不一致は、コード側とUXML側のどちらを直すべきか決まらないなら見送る）
- 設計逸脱のうち、クラスの分割・DI の再設計・責務の移動といった大きなリファクタになるもの（split-check / duplicate-check の担当領域、または別途の設計判断）
- パフォーマンス指摘のうち、計測なしに効果を判断できないもの（この環境ではプロファイルできない）

判断材料が足りないときは、聞く前に自分で埋める：該当コードと呼び出し元を読む、`git log -p` で意図的な変更かを確認する、`docs/` の該当ノウハウ（[docs/networking.md](../../docs/networking.md)・[docs/patterns.md](../../docs/patterns.md)・[docs/effects.md](../../docs/effects.md)・[docs/Live2D.md](../../docs/Live2D.md)）を読む。それでも決まらなければ見送る。

## Phase 3: 修正

直すと決めた箇所を Edit ツールで修正する。

修正時の注意：
- コーディング規約（CLAUDE.md）を守る：`_camelCase`、`var` 不使用、アクセス修飾子必須、波括弧必須・開き波括弧は新しい行
- 1つの指摘に対する修正は最小限に留める。ついでのリライト・整形はしない
- 深刻度「高」から順に直す。同一ファイルへの複数修正はまとめて行う

修正後の自己検証（コンパイルできないので読みで確かめる）：
- シグネチャや可視性を変えた場合、呼び出し元を Grep で全件確認する
- `Assets/Tests/` 配下から参照しているメンバーを変えていないか確認する（変えたならテスト側も追随させる）
- 追加した `using` が、そのアセンブリの asmdef で参照可能か確認する

---

## Phase 4: コミット

修正が完了したらコミットする。観点をまたいでいても 1 コミットにまとめてよい。

コミットメッセージの形式：
```
コードの問題を修正（<変更の要点>）
```

例：
```
コードの問題を修正（購読リーク・CancellationToken 伝播漏れ・var 違反を解消）
```

直す対象が無かった場合はコミットせず、その旨を報告して終了する。

---

## Phase 5: 報告

最後にまとめて報告する（確認ではなく事後報告なので簡潔に）。深刻度順に並べる。

提示フォーマット例（内容は架空）：

```
【コードチェック結果】対象: Assets/Scripts/ 全体

■ 修正した（コミット: a1b2c3d）
  1. [バグ/高] HomePresenter.cs:142
     Subscribe の戻り値を AddTo していなかった → destroyCancellationToken 側で破棄するよう修正
  2. [規約/中] MatchingService.cs:88
     ローカル変数の var を明示型に置き換え

■ 見送った（判断が必要）
  3. [設計/中] MatchingService.cs:55（要確認）
     Service 内で State を直接書き換えており単方向フローから逸脱。Model 経由に変えると
     責務の移動を伴うため見送り。直すなら Model 側に更新メソッドを足す形になる
  4. [パフォーマンス/低] HomePresenter.cs:30
     毎回 Q<T> を呼んでいるが、呼び出し頻度が低く効果が測れないため見送り

問題なしの観点: 規約（B）以外は指摘なし
```

- 見送った項目は「なぜ見送ったか」と「直すならどうするか」を 1 行添える
- 「要確認」で自分では確定できなかったものは、ここに集める

---

## 注意事項

- 判断に迷ったら「ユーザーに聞く」のではなく「見送って報告する」。手を付けた箇所は必ず根拠を持って直しきる
- 重複コードは指摘しない（duplicate-check の担当）。ファイルが大きすぎる件も指摘しない（split-check の担当）
- **テストが無いことそのものは指摘しない**（テスト設計は feature スキルの責務）。ただし既存テスト（[Assets/Tests/](../../Assets/Tests/)）が壊れる変更を見つけたら指摘・追随する
- 憶測で問題を捏造しない。読んで確定できないものは直さず見送りに回す
- 指摘は具体的に（ファイル・行・理由）。「なんとなく良くない」で終わらせない
