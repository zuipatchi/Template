# チェック系スキル共通の方針

`/feature`・`/ship`・`/code-check`・`/docs-check` が共通で従う方針。各スキルはこのファイルを参照し、スキル固有の基準だけを自分のファイルに書く。

---

## 1. 途中でユーザーに確認を求めない

- 調査から修正・コミットまで自分で完結させる（`/feature` は Phase 1 の承認だけが例外）
- 判断に迷ったら「ユーザーに聞く」のではなく **「見送って最後に報告する」**
- 手を付けた箇所は必ず根拠を持って直しきる。中途半端に片方へ寄せない

---

## 2. 調査エージェントの使い方

- `general-purpose` エージェント（`subagent_type: "general-purpose"`）を使う。**Explore エージェントは使わない**（コードの所在を探すためのもので、ファイルを抜粋でしか読まずレビュー・監査をしない前提のため、呼び出し元の追跡や照合が必要な調査に向かない）
- 観点が複数あるときは、1 観点 1 エージェントで**並列に** spawn する
- エージェントには必ず次を指示する:
  - 対象ファイルを**全文読む**こと（抜粋で判断しない）
  - 指摘する前に、呼び出し元・関連クラス・UXML/USS・LifetimeScope などを読んで**裏付ける**こと（名前の Grep ヒットだけで「存在する／しない」を決めない）
  - **調査のみ**行い、ファイルは一切編集しないこと
  - 憶測で問題を捏造しないこと。文脈次第で問題でない可能性があるものは確信度「要確認」にすること
- 各指摘は次の形で報告させる: **ファイルと行番号／観点／深刻度（高・中・低）／何が問題か（1〜2 文）／確信度（確実・要確認）／修正案（1〜2 文）**

---

## 3. 直す／見送るの共通基準

**直す**:
- 確信度「確実」で、修正が局所的（そのファイル・そのメソッド内、または同一アセンブリ内で影響範囲を Grep で洗い出せる）もの
- 機械的に直る規約違反・誤字・リンク切れ
- 正しい挙動が一意に決まるバグ修正、外部から見た振る舞いを変えないリファクタ
- 確信度「要確認」でも、**該当コードと呼び出し元を自分で読んで確実だと確定できた**もの（憶測のまま直さない）

**見送る**（手を付けず、理由と「直すならどうするか」を報告に残す）:
- 読んでも問題かどうか確定しないもの（意図的な実装の可能性が残るもの）
- 修正が**振る舞いの変更**・**仕様やプロダクト方針の決定**になるもの、正しい挙動が一意に決まらないもの
- 新しい共通クラス・インターフェースの新設、`public` / `internal` API の変更、アセンブリ（asmdef）をまたぐ移動など、**設計方針の決定**にあたるもの
- シーン（`.unity`）・Prefab・Addressables 側の変更が必要で、接続できる Unity Editor（`unity status`）が無いもの（YAML の手編集で直さない）
- 計測なしに効果を判断できないパフォーマンス改善
- ドキュメント全体の章構成を変えるような大規模な組み替え

**判断材料が足りないとき**は、聞く前に自分で埋める:
1. 該当コードと呼び出し元を読む
2. `git log -p -- <ファイル>` で、意図的な変更か・どちらが新しいかを確認する
3. `docs/`（[patterns.md](../../docs/patterns.md)・[effects.md](../../docs/effects.md) など）に意図が書かれていないか確認する

それでも決まらなければ見送る。

---

## 4. 修正時の注意

- コーディング規約（CLAUDE.md）を守る: `_camelCase`、`var` 不使用、`new()`、アクセス修飾子必須、波括弧必須・開き波括弧は新しい行
- 1 つの指摘に対する修正は最小限に留める。ついでのリライト・整形はしない
- 深刻度「高」から順に直す。同一ファイルへの複数修正はまとめて行う
- 内容を消すときは「削除済み」コメントを残さず記述ごと消す
- 修正後の自己検証（Unity でコンパイルできない前提で、読みで確かめる）:
  - シグネチャ・可視性・名前を変えたら、旧参照が残っていないか Grep で全件確認する
  - [Assets/Tests/](../../Assets/Tests/) から参照しているメンバーを変えていないか確認する（変えたらテストも追随させる）
  - 追加した `using` がそのアセンブリの asmdef で参照可能か確認する
  - 変更した `.cs` の csproj に `dotnet format <Project>.csproj --verify-no-changes --no-restore` を実行する

---

## 5. コミットと報告

- 今回の作業で変更したファイルだけを `git add` する（作業前から作業ツリーにあった無関係な変更は含めない）
- コミットメッセージは日本語。直す対象が無かった場合はコミットせず、その旨を報告する
- 報告は確認ではなく**事後報告**なので簡潔に、深刻度順に並べる:
  - **直したもの**（観点・ファイル・内容、コミットハッシュ）
  - **見送ったもの**（なぜ見送ったか・直すならどうするか。ユーザーの判断が必要なものはここに集める）
  - **問題なしの観点**

---

## 6. 技術バックログ

見送った項目と Unity での確認待ちの項目は [docs/tech-backlog.md](../../docs/tech-backlog.md) に記録し、セッションをまたいで引き継ぐ。

- **作業の最初に読む**。すでに載っている項目は再調査せず、「前回から状況が変わったか」だけ確認する。「検討済み・対応しない」の項目は、前提が変わっていない限り指摘しない
- 項目に「決定: 〜」が書き足されていたら、その方針で対応する（`/feature`・`/ship` は変更範囲に関係するものだけ、`/code-check`・`/docs-check` は該当する観点のもの）
- **見送った項目は追記する**（判断待ち／未確認／改善候補／検討済み・対応しない のどれかに分類し、新しい ID を振る。場所・内容・選択肢または直し方・出典（スキル名と日付）を書く）
- **解決した項目は削除する**（「解決済み」として残さない）
- tech-backlog.md の更新は、そのスキルのコミットに含める
- 作りたいゲームの仕様（[docs/game-backlog.md](../../docs/game-backlog.md)）はユーザーが書く場所。技術的な見送り項目を書き込まない
